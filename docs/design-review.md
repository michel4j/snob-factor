# Design Review: Concurrency & Performance Improvements in snob-factor

This document outlines a conceptual design review of the [snob-factor](file:///home/michel/Projects/snob-factor/src/snob-factor) codebase (C backend and Python wrapper) and proposes strategies to enable stable future concurrency improvements (e.g., safe OpenMP usage) and performance tuning.

Based on previous debugging attempts where OpenMP parallelization caused performance degradation and result discrepancies, the current codebase architecturally restricts thread-safety.

## 1. Global State Management & Reentrancy

**Current Architecture:**The codebase relies heavily on global variables defined in [src/glob.h](file:///home/michel/Projects/snob-factor/src/glob.h) (`NTypes`, `CurCtx`, `Samples`, `Populations`, `Scores`, etc.). C-functions implicitly access and mutate these global variables.- **Concurrency Issue:** In a multithreaded environment, multiple threads will read/write to these shared global states concurrently, leading to race conditions. If an OpenMP `#pragma omp parallel for` is wrapped around a loop that calls a function mutating global state, data corruption will occur.- **Python Wrapper Issue:** Because [__init__.py](file:///home/michel/Projects/snob-factor/snob/__init__.py) loads a generic shared object via `ctypes.CDLL('_snob.so')`, the entire Python process shares one global C state. Two [SNOBClassifier](file:///home/michel/Projects/snob-factor/snob/__init__.py#161-439) instances fitting concurrently in the same Python process will clobber each other.

**Proposed Improvement: Opaque Context Pointers**Refactor the C library to be fully reentrant by eliminating global variables.- Group the global state into a dedicated structure, e.g., `typedef struct SnobModel { ... } SnobModel;`.- Modify all core functions ([do_all](file:///home/michel/Projects/snob-factor/src/doall.c#410-470), [do_case](file:///home/michel/Projects/snob-factor/src/doall.c#620-854), [classify](file:///home/michel/Projects/snob-factor/snob/__init__.py#490-520), etc.) to accept this context as their first argument: `int do_case(SnobModel* model, int item, int all, ...)`.- For the Python API, return a pointer to this model upon initialization (`handle = lib.initialize_model()`), and pass it to subsequent calls. This solves Python-level thread safety and paves the way for C-level task parallelization.

## 2. Random Number Generation (RNG) State

**Current Architecture:**The PRNG functions in [doall.c](file:///home/michel/Projects/snob-factor/src/doall.c) ([rand_int()](file:///home/michel/Projects/snob-factor/src/doall.c#9-15), [rand_uint()](file:///home/michel/Projects/snob-factor/src/doall.c#16-24), [rand_float()](file:///home/michel/Projects/snob-factor/src/doall.c#25-33)) rely on a globally shared state (`RSeed`).- **Concurrency Issue:** If multiple threads generate random numbers simultaneously, they cause race conditions on `RSeed`. If `RSeed` is protected by a lock (mutex/atomic), it becomes a massive performance bottleneck. If accessed concurrently without synchronization, the sequence of pseudo-random numbers is corrupted, drastically altering the algorithmic convergence and destroying reproducibility.

**Proposed Improvement: Thread-Local RNG State**- Switch to a reentrant PRNG model. Instead of a global `RSeed`, give each thread its own independent PRNG state.- If using OpenMP, allocate an array of seeds: `unsigned int seeds[MAX_THREADS];` initialized uniquely per thread. When generating a number inside a parallel region, use `rand_r(&seeds[omp_get_thread_num()])` or a faster custom PRNG like PCG or Xoshiro256+ with the thread-local state.

## 3. Safe Parallelization with OpenMP

**Current Architecture Limitations:**Parallelizing inner loops directly requires care to avoid accumulating values into shared variables without synchronization.

**Proposed Improvements:**- **Reduction Operations:** Operations like recalculating costs or accumulating error scores must use appropriate OpenMP reductions (e.g., `#pragma omp parallel for reduction(+:total_cost)`).- **Avoid False Sharing:** If threads are updating discrete arrays (like class scores), ensure that different threads don't frequently update adjacent memory locations residing on the same cache line. You can pad the data structures or ensure data chunking matches cache line sizes.- **Coarse-Grained vs Fine-Grained Locks:** Avoid locking inside tight innermost loops. Instead, compute partial results in thread-local storage, and merge them safely at the end of the loop block.- **Parallelize Outer Loops:** E.g., parallelizing over individual *cases* or *samples* during the assignment step rather than parallelizing the tiny math operations inside a single case. [do_case()](file:///home/michel/Projects/snob-factor/src/doall.c#620-854) is a prime candidate if the shared context is read-only or cleanly reduced.

## 4. Algorithmic Data Locality

**Current Architecture:**The codebase has many pointer indirections (like `Class *Sons[MAX_CLASSES]`, `VarSets`, etc.), which can mean fragmented heap allocations.- **Performance Issue:** Pointer chasing degrades CPU cache utilization.

**Proposed Improvement: Struct-of-Arrays (SoA) vs Array-of-Structs (AoS)**- If operations iterate over specific attributes over all records (e.g., adjusting scores across columns), reshaping data into a flat Struct-of-Arrays could allow SIMD vectorization and much better cache locality.
